## 优先修正的三个问题

### 1. 纯店铺标题规则正在误伤含商品描述的标题

`smzdm.py:268` 的规则为：

```python
r"^.{1,30}(?:官方)?(?:京东自营)?旗舰店\s*$"
```

它只要求标题长度和旗舰店后缀，没有确认前面是否已经包含商品。

[最新运行](https://github.com/CallMeByYourName/smzdm-monitor/actions/runs/38035507023)的 Run scraper 日志第 76–77 行直接显示以下标题被此规则过滤：

- `海尔 空调小2匹挂机壁挂式新一级能效变频客厅家用官方旗舰店`
- `海尔 空调3匹AI舒适风Pro家用一级能效柜机E2旗舰店`

最近 100 次中，此规则触发 152 次，包含 16 个不同截断标题。其中 15 种标题包含明确商品描述，累计 148 次过滤；还有沐浴露、德芙巧克力、立邦美缝剂等。这是标题分类过宽的证据。日志没有这些文章的 ID 和互动字段，不能进一步声称它们都本应推送；实时总榜也没有找到上述两条海尔文章。

建议收窄纯店铺规则，补这类商品标题的允许样本，同时保留 `养生堂京东自营旗舰店` 等纯店铺标题的拒绝样本。修正重点是保护商品描述，不能把所有旗舰店后缀都当作任务入口。标题过滤在保存快照之前执行，被误伤的文章也无法进入后续趋势和延迟复查。

### 2. 不同文章的互动计数被混用为同一条趋势

`smzdm.py:1567` 的趋势 key 优先采用 SKU 或标题指纹；`smzdm.py:1389` 查询历史时只按 `item_key`，未限制 `article_id`。同一商品的不同爆料有各自独立的评论、收藏和值票，不能直接相减作为增长。`smzdm.py:1514` 每轮保存快照也按此 key 去重。

离线内存 SQLite 复现：

| 文章 | 观察时间 | 评论 | 收藏 | 值 |
| --- | --- | ---: | ---: | ---: |
| A，同一商品指纹 | 30 分钟前 | 1 | 4 | 4 |
| B，不同文章 ID，首次观察 | 当前 | 5 | 6 | 5 |

当前代码把 B 算成增长 23 分、新增 1 个值票，并让它以“升温好价”通过。清除 A 的历史后，B 正确被初筛拒绝。这是已复现的代码缺陷；日志未记录趋势基准文章 ID，尚不能计算线上影响次数。

建议让趋势查询、快照防重和文章观察窗口按 `article_id` 隔离，商品去重继续使用 SKU/指纹。兼容旧数据库时，可先在历史查询中限制文章 ID，再迁移旧 key；必须补“同商品不同文章不能借用增长”和“同文章真实增长可以通过”的对照测试。

### 3. 推送成功判断缺少接收人状态校验

`smzdm.py:3093` 仅检查外层 `success`，没有校验返回 `data` 中目标 UID 的 `code`。随后 `run()` 会把该文章写入成功历史。

[WXPusher 官方文档](https://github.com/wxpusher/wxpusher-docs/blob/master/docs/README.md)说明，返回数组包含每个 UID 的发送状态，`code=1000` 表示成功，并提供 `sendRecordId` 用于查询状态。外层调用成功不能替代目标接收人的状态。

离线 Mock 外层 `success=true`、目标 UID `code=1001` 时，现有函数仍返回 `True` 并打印“推送成功”。这可能使发送失败的文章进入历史，阻止后续重试。近期日志没有保存返回数组，尚无证据证明已经发生实际漏送；上述 268 条指应用记录的成功，不能当作逐条已到达终端的证明。

建议校验目标 UID 的成功状态，再写历史；记录 `sendRecordId` 和接收人状态码，区分接口接受、异步投递状态与用户阅读。超时结果仍可能未知，不应新增无条件立即重发。

## 后续优化与观察项

**补齐可追溯日志，优先于继续调阈值。** 标题拒绝、评论拒绝、趋势等待和慢增长日志应统一包含文章 ID、来源、完整或可定位标题。评论硬拒绝应记录声明总数、返回样本数、作者排除数、覆盖率；趋势日志应记录基准文章 ID 与快照时间。增加推送失败计数，使 Actions 绿色状态与业务发送结果可以分别审计。

**减少重复评论请求，但避免长期锁定旧结论。** 最近 100 次，某个比比赞鸡肉肠截断标题出现 15 次评论硬拒绝。可以在互动和评论总数不变时短期复用样本，并在增长或 TTL 到期时重新获取。需要先补文章 ID 才能量化节省请求数，也不宜永久缓存负面结果。不能直接把趋势检查全部移到评论请求之前：本轮有 56 次评论总数被模块升级，升级可能影响最终放行。

**保留缺样本降级原则，观察已有异常证据的后续变化。** 268 条推送中，47 条有评论等级通过记录，221 条通过样本不足、覆盖不足或明确跳过后继续使用互动与趋势筛选，约 82.5%。这符合当前策略，不能解释成 82.5% 质量差。比比赞鸡肉肠在[00:18 的运行](https://github.com/CallMeByYourName/smzdm-monitor/actions/runs/37957766152)仍因低等级 2/3 被拒，在[11:33 的运行](https://github.com/CallMeByYourName/smzdm-monitor/actions/runs/38020793891)变成 6/9 覆盖不足，靠增长通过，ID 为 `183677696`。可以先记录“此前观察到等级异常”的诊断标识，核实是否同一批样本，再决定有限时长的风险提示；不应据此把缺失数据变成硬拒绝。

**延迟复查有效，先提高选择效率。** 1,407 次请求检查了 1,017 个不同文章 ID，最终补回 25 次推送，占总推送约 9.3%；每次请求的直接推送转化约 1.8%。队列每轮为 258–501 条，请求 11–16 次。在现有请求上限内，可以研究距阈值差距、近期增长和重复复查收益，配合保留首次检查与临近过期候选的保底机会。现在的队列主要按期限排序，仅凭转化率低不足以取消兜底，也不建议直接提高外部请求上限。

**缓存与运行时风险应分级处理。** 最近 100 次缓存全部恢复、保存成功，99 条相邻缓存链都接上紧邻前一轮，未发现缓存倒退或同 ID 重推。当前 API 列出了 738 份缓存、约 9.17 GB 总体积，按 run ID 保存数据库会持续产生版本；有长期持久化需求时，可考虑稳定状态存储，但不要声称缓存已引起故障。另离线验证发现 `respect_retry_after_header=True` 会对带 Retry-After 的 429 自动重试，`Retry-After:3600` 可等待一小时，绕过预期的及时熔断；建议限制该等待或让 429 直接进入现有熔断。近期没有这一风险的线上发生证据。
