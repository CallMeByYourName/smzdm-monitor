# 什么值得买 (SMZDM) 好价监控推送系统

基于 GitHub Actions 的单次扫描脚本。它抓取什么值得买好价列表，先用互动数据筛出候选，再通过评论用户等级、评论用户集中度、互动异常、相似商品去重和降价判断，尽量减少水军爆料和重复推送。

本文档按 `2026-07-20` 的代码与工作流配置更新；实际阈值以 `smzdm.py` 中的 `CONFIG` 为准。

## 当前逻辑

### 1. 数据源

- 主列表接口：`https://api.smzdm.com/v1/list?limit=100&offset=N`
- 3/12 小时热榜补充：`https://m.smzdm.com/sou/category_rank?page=1&limit=20&hour=N`
- 频道列表补充接口：`https://api.smzdm.com/v1/faxian/list?...&version=2`、`https://api.smzdm.com/v1/youhui/list?...&version=2`
- 只扫描 `faxian`、`youhui` 两类频道。
- 主列表负责发现候选和读取互动数据；频道列表用于补充 `article_link`、`article_mall_client.mall_no`、`article_mall_client.product_no`。这些字段不是每条都有，脚本只在接口能提供时使用。
- 主列表每页读取接口实际支持的 100 条上限，最多 40 页/4000 条和过去 6 小时数据，减少请求次数及实时分页漂移；热榜按半小时窗口在 3 小时榜和 12 小时榜之间轮换，每轮仍只请求一个榜单的前 20 条。3 小时榜用于更早发现短期升温，12 小时榜用于补回发布较早、近期重新升温的商品。热榜商品不会直接推送，仍需经过相同的标题、互动质量、评论、趋势和去重规则。
- 脚本是单次运行模式：扫描 -> 筛选 -> 推送 -> 退出，没有常驻循环。

### 2. 第一阶段：互动评分初筛

综合评分公式：

```text
综合评分 = 评论数 * 3 + 收藏数 * 2 + 值票数 * 1
```

当前有六条放行路径：

| 路径 | 门槛 | 用途 |
| --- | --- | --- |
| 超级好价 | 评论 >= 20，值 >= 20，收藏 >= 10，综合评分 >= 120，好评率 >= 90% | 高值率、高评论、高收藏和值票的确定性好价 |
| 均衡热度 | 评论 >= 6，值 >= 8，收藏 >= 5，互动 >= 25，综合评分 >= 65，好评率 >= 90% | 三类互动都较完整的成熟商品 |
| 高讨论 | 评论 >= 12，值 >= 8，收藏 >= 5，互动 >= 30，综合评分 >= 90，好评率 >= 85% | 讨论充分且值票、收藏也达到门槛的商品 |
| 早期好价 | 值 >= 4，评论 >= 6，收藏 >= 4，互动 >= 16，综合评分 >= 35，好评率 >= 95% | 当前信号较好，并等待后续值票/收藏增长确认 |
| 早期强信号 | 值 >= 6，收藏 >= 8，互动 >= 16，综合评分 >= 28，好评率 >= 95% | 评论可能还在审核，以值票/收藏增长确认 |
| 升温好价 | 值 >= 4，收藏 >= 4，互动 >= 15，综合评分 >= 32，好评率 >= 95%，且历史快照中至少新增 1 个值票 | 不允许只靠评论或收藏增长进入升温路径 |

基础要求：值票至少 2 或评论至少 2。售罄、过期、已结束会直接过滤。

脚本不做大范围标题关键词和分类/tag 硬过滤。流量卡、红包、券、运营商、金融等内容如果互动质量达标，会继续进入后续判断；这类内容建议在 WXPusher 侧用关键词屏蔽。

但 WXPusher 只能做普通关键词，无法表达“入会%京豆”这种中间内容可变的规则。脚本会先归一化全角数字、带方框/按键的数字等常见变体，再拦截任务动作和奖励语境，例如：

- `入会...京豆`
- `入会5豆`
- `关注...1豆`、`关注...京豆`
- `关注领京豆`
- `签到...京豆`、`签到100豆`
- `得10京豆`、`领10京豆`、`送10京豆`
- `抽奖50豆`、`大转盘...50豆`、`竞猜瓜分2万京豆`
- `店铺领5️⃣`、`直播5豆`、`关注45D`、把“豆”写成“逗”的签到/抽奖标题
- 店铺名后只有 `加购/如图`、`共计二十个豆`、`有2 0` 等操作或奖励话术
- `来来来这是一百的` 等没有明确商品主体的含糊标题
- `店铺活动（加购 10）`、`店铺会员入会50`、`积分兑10豆`、`京自领京豆` 等只有店铺任务或奖励、没有可购买商品的标题
- `积分兑换二十五豆`、`专区有二十豆`、`等级礼包五十豆` 等中文数字或拆分数字变体
- `进入弹窗可领随机卡/优惠券`、`10元e卡抽奖`、只有品牌参与信息的促销页
- `积分兑换京豆`、`加购商品得京豆`、`入会20`、`每日一豆` 等省略奖励单位或混入店名的任务
- `弹窗可领红包`、`参加活动非必中`、`深夜游乐场` 等会场、抽奖或含糊活动标题

`入会专享`商品、名称中含“大转盘”的玩具等不会仅凭单个词过滤；任务动作必须同时带有京豆、红包、积分、实测中奖等明确奖励语境。`评论有奖`、`会员积分兑换实物` 等非商品活动会过滤。

单字动作不会脱离奖励单位判断：`圆领...型号D`、`抽油烟机...92D`、品牌名中的“得”和商品名“聚力豆”等不会再被当成领豆任务。

成功推送日志会同时记录文章 ID、价格、筛选路径和互动指标，便于后续从 Actions 日志复盘具体商品。

### 3. 候选快照和趋势评分

脚本会把有基础互动信号的商品写入 SQLite `candidate_snapshots` 表，默认保留 2 天。每次扫描时，同一商品会和历史快照比较，计算：

- 值票增长、收藏增长、评论增长。
- 总增长分：评论增长权重最高，其次是值票和收藏，不值票增长会扣分。
- 最近一轮增长分。
- 是否出现“发布一段时间后互动停滞”的水军嫌疑。

`升温好价` 依赖这些增长数据。这样刚发布时评论还没审核出来的商品不会被早期评论数误伤；反过来，初始自带一些值和收藏、但后续不增长且评论仍少的商品会被降噪。

趋势现在不只是展示和加分，也会参与筛选：

- 低信心早期商品（`早期好价`、`早期强信号`）第一次出现时先保存快照。下一轮必须出现足够快的互动增长，并且至少新增 1 个值票，才会推送；当前数据已经成熟且分布均衡（评论至少 10、综合分至少 65、值至少 6、收藏至少 8），或讨论热度已经充分（评论至少 20、综合分至少 100、值至少 4、收藏至少 8）时可直接通过，避免因最近半小时没有新增值票而无限等待。
- `升温好价` 必须满足近期增长，或在较短累计窗口内达到足够的增长速度，而且至少新增 1 个值票。只增加评论或收藏、或超过几小时才慢慢涨一点的商品不再进入升温路径。
- 已有历史快照、观察至少约 25 分钟、评论仍少、总增长分和最近增长分都偏低的商品会被“增长过低过滤”。
- 如果观察窗口已经很长、评论仍少、最近一轮几乎不涨、累计增长速度也很低，会触发“增长过慢过滤”。
- `超级好价`、`高讨论` 不受低增长/增长过慢过滤影响。

### 4. 评论等级和评论集中度检测

对初筛候选调用移动端详情模块：

```text
https://haojia.m.smzdm.com/detail_modul/user_related_modul?article_id={article_id}
```

从返回 JSON 中读取评论用户的 `vip_level`、`user_smzdm_id`、`display_author` 和模块里的 `author_smzdm_id`。这个模块不是完整评论分页，通常只返回热评/相关评论样本；脚本会记录模块声明的评论总量、原始样本数、作者评论数和非作者样本数。

如果详情模块声明的评论总数高于列表 API 评论数，脚本会用模块总数更新当前商品的评论数和综合评分。这样像列表只显示少量评论、详情里实际已经有大量评论的商品，不会因为列表数据滞后而继续按“样本不足/早期商品”处理。

脚本会先判断评论模块覆盖率：用 JSON 中实际返回且带等级信息的去重评论节点数，对比 `max(列表 API 评论数, 模块声明总评论数)`。只有返回样本覆盖总评论数约 80%，或两者差距不超过 2 条时，才把这些样本视为可代表整体评论区，并继续做等级/集中度判断。若总评论数已达到 10 条，但模块只返回少量热评或作者补充，脚本会跳过评论等级水军判断，避免用几条热评误判大评论区。

- Lv5 及以下视为低等级账号。
- Lv6 及以上视为更可信账号。
- 低等级评论用户占比超过 35% 时过滤。
- 可取评论样本达到 4 条后，会检查评论是否集中在少数用户：
  - 独立用户少于 3 个时过滤。
  - 单个用户评论占比超过 50% 时过滤。
- 如果评论模块覆盖率足够，且成熟商品只能取到 2 条非作者评论样本，但两条都是 Lv6+ 且来自不同用户，同时商品好评率 >= 85%，并且评论数 >= 10 或综合评分 >= 80，则允许少样本通过。
- 如果评论模块覆盖率不足，不再默认阻断推送；脚本会记录评论覆盖诊断，最终主要按互动评分和增长趋势判断。
- 普通早期好价不走少样本通过，避免用少量热评样本误判。
- 早期强信号考虑到 SMZDM 评论审核延迟：当列表评论数低于评论等级判断门槛时，会跳过评论等级判断并继续后续流程；如果评论数已经足够，仍会尝试读取评论等级。

### 5. 评论等级不可用时

评论接口可能返回样本不足、触发外部熔断，或本轮评论校验预算耗尽。现在评论等级不可用只作为诊断信息，不再默认暂缓已经通过互动/趋势评分的商品。

- 本轮评论校验预算是动态计算的：常规情况下校验全部可校验候选，最高 80 条，避免预算不足造成额外半小时级延迟。
- 评论等级不可用时，推送内容会显示评论判断说明。
- 只有当评论样本覆盖足够、且低等级占比或用户集中度明确异常时，评论等级才会作为硬过滤。
- 旧的 `pending_reviews` 表仍保留兼容，但默认策略已经不依赖评论不可用暂缓。

### 6. 互动异常兜底

当总投票数达到 30 后，脚本会检查两个异常信号：

- 值/不值比例超过 20。
- 评论数/值票数低于 0.2。

同时命中 2 个异常信号才会判定为水军嫌疑并过滤。

另外，如果一个商品已经被多轮扫描观察到，发布超过 60 分钟后值/收藏/评论几乎没有增长，且评论仍很少，会触发更严格的“增长停滞过滤”。

### 7. 去重和降价再推送

- 只有推送成功的商品才写入 `history`。
- 同一文章 ID 已推送过会跳过。
- 如果频道列表提供了平台商品号 `article_mall_client.product_no`，会生成平台 SKU key，并优先按同 SKU 去重。
- 相似标题会生成商品指纹，30 天内默认只推一次。
- 标题中的价格金额会归一化后再生成指纹，不会因为 `19元套餐`、`22.5元/斤：商品名` 等价格位置导致指纹缺失或重复推送。
- 如果同 SKU 或同指纹商品价格比历史推送低至少 5 元，或降幅至少 5%，允许再次推送，并在推送内容里标记降价信息。
- 未推送或推送失败的商品不会写入历史，下次扫描仍可结合最新互动和候选快照重新评估。

### 8. 京东商品处理

京东自营强校验当前默认关闭。原因是 GitHub Actions 访问京东或跳转页时经常拿不到稳定的店铺/自营字段，强行过滤会误伤好价。

现在京东商品和其他平台一样，统一走互动评分、评论等级、评论集中度、互动异常和去重逻辑。

### 9. 反爬和稳定性

- 外部详情/评论请求有随机延迟。
- 如果遇到 `202/403/429`、验证码、`probe.js`、访问频繁等标记，本轮会熔断外部校验。
- 熔断后不再继续请求详情/评论接口，降低触发反爬的风险。
- HTTP 请求最多重试 2 次，连接/读取超时分别为 8/20 秒。主列表连续 3 页失败会结束本轮，评论接口连续 2 次失败会熔断外部校验，由下一轮定时任务继续，避免网络故障把扫描阻塞数小时。

## 运行

```bash
pip install -r requirements.txt
WXPUSHER_APP_TOKEN=xxx WXPUSHER_UID=xxx python3 smzdm.py
```

可选环境变量：

- `WXPUSHER_APP_TOKEN`：WXPusher app token。
- `WXPUSHER_UID`：接收推送的 UID。
- `SMZDM_DB_PATH`：SQLite 数据库路径，默认 `smzdm.db`。

## 测试

```bash
python3 -m unittest -v
```

当前测试覆盖分页和热榜轮换、任务活动标题过滤及商品标题防误伤、互动路径、趋势确认、评论覆盖率、去重降价和推送日志字段。修改筛选阈值或正则后，应先补充对应样本并运行完整测试。

## GitHub Actions

`.github/workflows/smzdm.yml` 当前配置：

- 由 cron-job.org 每 15 分钟触发一次；工作流不再同时配置 GitHub schedule，避免两套定时器造成重复扫描。
- 支持 `workflow_dispatch` 手动触发。
- 支持 `repository_dispatch`，可由 cron-job.org 请求 GitHub API 触发。
- SQLite 数据库通过 `actions/cache` 恢复和保存。
- 使用 `concurrency: smzdm-scan` 避免同仓库扫描任务并发执行。
- 单次任务最长运行 12 分钟，避免故障任务占住后续 15 分钟扫描窗口。

注意：`actions/cache` 不是严格的可变数据库存储。如果多个运行非常接近，仍可能恢复到较旧缓存，导致短时间重复推送。长期更稳的方案是把状态保存到专门的 state 分支、artifact 或外部 KV/数据库。

## 推送内容

WXPusher 使用 HTML 内容，包含：

- 热度标记：`💎超`、`🔥爆`、`📈升`、`👍热`、`🆕新`
- 平台、标题、价格、发布时间
- 好评率、综合评分、值/不值/评论/收藏
- 值、收藏、评论相对历史快照的增长情况
- 当历史窗口过长时，只展示最近一轮增长；没有近期增长时不展示长窗口累计增长
- 评论总数是否由详情模块更新
- 评论模块覆盖率，例如返回评论数/模块总评论数，以及覆盖是否足够
- 评论等级和评论用户集中度统计
- 降价再推送说明
- SMZDM 详情链接

## 文件结构

- `smzdm.py`：主脚本。
- `test_smzdm.py`：筛选、趋势、评论、去重和推送行为的单元测试。
- `requirements.txt`：运行依赖，目前只有 `requests`。
- `.github/workflows/smzdm.yml`：GitHub Actions 工作流。
- `README.md`：面向使用者的现行规则和部署说明。
- `AGENTS.md`、`CLAUDE.md`：面向代码代理的开发约束与架构说明。
- `analysis/`：按日期保存的历史日志分析和反馈样本；其中的旧阈值只代表生成当时的代码。
- `smzdm.db`：运行时 SQLite 数据库，本地和 Actions 缓存使用。
